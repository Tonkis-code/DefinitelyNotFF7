  What your four endpoints have in common

  Each action endpoint (attack, ability, defend, potion) does the same five
  steps:

  1. Validate: does a battle exist, and is it still going?
  2. Player acts: ← the only step that really differs
  3. Enemy responds if it's still alive
  4. CheckWinner
  5. HandleBattleOutcome

  When most of a method is identical and only one step changes, the usual fix is
  to make the action data, not a route. The client stops picking a URL and
  sends a description of what it wants to do. One endpoint (for example POST 
  /api/battle/turn) runs the shared steps once and branches only at step 2.

  This is called the Command pattern: an action becomes an object you can pass
  around, check and run.

  A parallel example (a card game, not your battle)

  public enum CardActionType { Play, Discard, Draw }

  public class CardActionRequest
  {
      public CardActionType Type { get; set; }
      public string? CardId { get; set; }   // only needed for Play/Discard
  }

  [HttpPost("turn")]
  public IActionResult TakeTurn([FromBody] CardActionRequest request)
  {
      // shared validation goes here, once
      switch (request.Type) { /* only the action-specific part */ }
      // shared "end of turn" steps go here, once
      return Ok(result);
  }

  Why this works:
  - [FromBody] tells ASP.NET to build CardActionRequest from the JSON body, e.g.
    { "type": "Play", "cardId": "fireball" }. Swagger will show you a form for
    it. Enums are sent as numbers by default; to accept "Play" you register a
    JsonStringEnumConverter, which is worth looking up.
  - string? marks a field that only some actions use. Attack doesn't need an
    ability name, but an ability action does.
  - The parts that never change now exist once. If you add a "poison ticks at
    end of turn" rule later, you write it in one place instead of four.

  Two things in your code to think about before you refactor

  1. Defend doesn't follow the pattern. It does the enemy's hit itself, inside
     BattleService.Defend, while every other action leaves that to the
     controller. In a single turn pipeline, how would you handle this? Hint:
     what if the player's action could change how the enemy's hit lands, instead
     of doing the hit itself?
  2. Your action methods return damage, and the controller throws it away. Once
     you have one turn endpoint, a natural follow-up is returning a turn result,
     like a small log of what happened ("player dealt 24", "enemy dealt 10").
     This is what will make the Phaser frontend feel smooth, because it can
     animate each event in order instead of just showing new HP numbers. It
     would also fix the inconsistent response shape from /potion.

  My advice: start simple with an enum plus optional fields, like the example.
  .NET also supports polymorphic JSON, where each action is its own class, but
  that's more machinery than you need right now.

  What goes in the middle

  The middle is just a switch on the action type. Each case holds only what
  makes that action different from the others. Picture the method in three
  zones:

  TakeTurn(request)
  │
  ├─ ZONE 1: shared checks (every action)
  │    battle exists? battle not over?
  │
  ├─ ZONE 2: switch (request.Type)
  │    case A: action-specific checks, then call the service method for A
  │    case B: action-specific checks, then call the service method for B
  │    default: return BadRequest
  │
  └─ ZONE 3: shared end of turn (every action)
       enemy responds, check winner, handle outcome, return result

  You don't write any new game logic. Every case is code you already have. Cut
  the action-specific lines out of each old endpoint and paste them into their
  case.

  Here it is in the card game example:

  switch (request.Type)
  {
      case CardActionType.Draw:
          if (deck.IsEmpty) return BadRequest("Deck is empty.");   // only Draw 
  cares about this
          cardService.Draw(game);
          break;

      case CardActionType.Play:
          if (request.CardId == null) return BadRequest("No card chosen.");
          cardService.Play(game, request.CardId);
          break;

      default:
          return BadRequest("Unknown action.");
  }
  // after the switch: code every action shares

  Why this works: break doesn't leave the method. It just jumps out of the
  switch and continues into Zone 3, so every action gets the same end of turn
  for free. A return inside a case stops the whole request early, which is what
  you want when a check fails.

  There's one side effect worth knowing. If you write

  shorter property name like Action or Type, so the switch reads switch
